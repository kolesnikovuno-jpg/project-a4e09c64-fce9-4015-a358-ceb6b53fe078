# Egg Engine v0.2 — серверное хранение и внешний интерфейс команд

**Статус:** подготовлено в тестовой ветке. Схема базы **не применена**, серверный сервисный ключ **не настроен**, опубликованный API пока должен возвращать \`503 egg_engine_not_configured\`. Это намеренное закрытое состояние, не ошибка интерфейса. Данные нынешнего визуального прототипа остаются в браузере; автоматической миграции в облако ещё нет.

## Для чего этот слой

Целевой принцип: Автор общается с *привычным* ИИ, ИИ обращается к независимому движку «Яйцо», движок фиксирует вопросы и результаты. Только Автор утверждает значимые изменения Ядра и переходы между уровнями. Нет обязательного второго чата и нет требования передавать всю историю общения/память другому сервису.

### Что реализовано

- \`api/egg.ts\` — один Vercel HTTP endpoint \`/api/egg\` (GET / POST), no CORS wildcard, no-store, ограниченный JSON.
- \`src/lib/eggCommands.ts\` — проверяемые типы и правила разрешённых команд.
- \`supabase/migrations/20261102235000_egg_engine_tables.sql\` — подготовленная схема хранения проектов и временных ключей с серверным закрытием таблиц.
- \`src/test/EggCommands.test.ts\` — проверки маршрутов, авторства и ограниченного доступа.
- \`vercel.json\` — маршрут \`/api\` теперь исключён из SPA-редиректа.

### Акторы и границы

**Сессия Supabase Auth (JWT).** API проверяет её через сервер Supabase Auth. Владелец получает права Автора на *свои* проекты: создать проект, создать/отозвать AI-ключ, принять/отклонить вывод, выбрать уровень и итерацию.

**Scoped Egg access key.** Внешний ИИ использует **не пароль и не пользовательскую сессию**, а отдельный \`egg_v1_\` ключ с ограничениями:
- только **один проект**;
- только чтение и внесение вопросов/выводов;
- срок **1–30 дней**, возможность отзыва;
- хранится только SHA-256 хеш, исходный ключ возвращается Автору один раз;
- не может создавать проекты, выпускать ключи, выносить решения Автора или менять уровень.

**ВАЖНО:** пользовательский Supabase JWT нельзя передавать внешнему ИИ. Он даёт авторские полномочия. Внешнему ИИ передаётся только scoped access key.

### Жизненный цикл

1. Автор входит через будущую интеграцию Supabase Auth и вызывает \`create\`: передаёт зерно, движок создаёт проект уровня 1.
2. Автор создаёт \`issue_key\` для выбранного проекта и один раз передаёт ключ подключённому внешнему ИИ через разрешённую конфигурацию инструмента.
3. ИИ делает GET состояния, передаёт вопросы по существующему графу сфер с \`route\`, отмечает работу \`start\`, возвращает гипотезы/наблюдения \`return\`.
4. Автор в доверенном интерфейсе подтверждает или отклоняет результат \`decide\`; ИИ не имеет этой команды по ключу.
5. При подтверждении нового уровня Автор вызывает \`set_level\` либо \`next_iteration\`.
6. Автор отзывает ключ через \`revoke_key\`, например, если сменил ИИ.

### HTTP контракт (описание, не готовое подключение ChatGPT)

Запросы имеют \`Authorization: Bearer <token>\`, где token — либо проверенный Supabase JWT владельца, либо scoped Egg key. В URL ключ не передаётся.

- \`GET /api/egg?projectId=<uuid>\`: состояние Ядра, сфер, задач, событий и \`revision\`.
- \`POST /api/egg\` с JSON \`{"command":"create","seed":"..."}\`: **только Автор**, возвращает \`projectId\`, \`revision\`.
- \`{"command":"issue_key","projectId":"...","label":"Claude","expiresInDays":7}\`: **только Автор**, выдаёт одноразовый \`accessKey\`.
- \`{"command":"revoke_key","projectId":"...","keyId":"..."}\`: **только Автор**.
- \`{"command":"route","projectId":"...","expectedRevision":1,"from":"idea","to":"marketing","question":"Кому нужен продукт?"}\`: вопрос разрешённой сфере.
- \`{"command":"start","projectId":"...","expectedRevision":2,"taskId":"task-2"}\`: сфера приступила к работе.
- \`{"command":"return","projectId":"...","expectedRevision":3,"taskId":"task-2","text":"...","evidence":"hypothesis","sourceRefs":["..."]}\`: возвращён вывод с происхождением.
- \`{"command":"decide","projectId":"...","expectedRevision":4,"taskId":"task-2","outcome":"accept","reason":"Принимаю как гипотезу"}\`: **только Автор**.
- \`{"command":"set_level","projectId":"...","expectedRevision":5,"level":2,"reason":"Автор подтвердил переход"}\`: **только Автор**.
- \`{"command":"next_iteration","projectId":"...","expectedRevision":6,"reason":"Уточнение формы"}\`: **только Автор**.

При устаревшем \`expectedRevision\` сервер отвечает \`409 revision_conflict\`, клиент заново читает актуальную версию и предлагает пользователю разрешить конфликт, а не перезаписывает чужое решение.

### Как включить безопасно (НЕ выполнено автоматически)

1. Создать/выделить тестовую базу Supabase или подтвердить отдельную схему в существующем тестовом проекте; перед выполнением миграции проверить возможные конфликты и права.
2. Применить файл SQL миграции, включающий закрытые таблицы и \`egg_engine_cas_update\` с атомарной проверкой ревизии. В текущем контуре эта миграция **только хранится в GitHub**.
3. Настроить для **preview** Vercel: \`EGG_SUPABASE_URL\` (или существующий \`VITE_SUPABASE_URL\`), \`EGG_SUPABASE_PUBLISHABLE_KEY\` (или \`VITE_SUPABASE_PUBLISHABLE_KEY\`) и **\`SUPABASE_SERVICE_ROLE_KEY\`**. Service-role key не должен попадать в \`VITE_*\`, исходники, журнал диалога, URL или публичные ответы.
4. Подключить авторскую сессию к отдельной странице управления. Существующая страница Автора пока не сохраняет проекты через сервер.
5. Проверить авторизацию на реальном проекте: чужой пользователь не видит документы; AI-ключ не может утвердить решение; отзыв ключа немедленно закрывает доступ; конфликт версий возвращает 409.
6. Добавить rate limit, quotas, резервные копии, экспорт, наблюдаемость, управление расходами и пользовательское согласие для передачи данных внешнему ИИ — до коммерческого запуска.

### Что НЕ реализовано

- Автоматическая миграция данных старого интерфейса/локальных эскизов из IndexedDB.
- Синхронизация визуальных сфер с новым серверным состоянием.
- Публичное распространение API-ключей или рабочее подключение через MCP/ChatGPT/Claude.
- Оплата, тарифы, учёт токенов и затраты.
- Техническая/правовая сертификация решений сфер.
- **Защита от всех типов повторного выполнения**: проверка ревизии снижает риск перезаписи, но полноценная идемпотентность команд остаётся следующим слоем.

**Проверять прежде всего права доступа и качество истории решений, а не число API-методов.**
