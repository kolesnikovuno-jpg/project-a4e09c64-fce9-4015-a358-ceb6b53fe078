# Яйцо v1.0 (тест) — Автор → независимая серверная база

**Дата:** 2026-11-03. **Ветка:** prototype/design-brief-sketch-gates.

**Цель:** первый контролируемый цикл: Автор входит через отдельный Supabase Auth → создаёт серверный проект из зерна → читает его обратно → вручную регистрирует ссылку Google Drive → подтверждает как Автор.

## Где находятся границы

- Движок: \`src/lib/eggEngine.ts\`, \`src/lib/eggCommands.ts\`. Не зависит от Lovable.
- Сервер: \`api/egg.ts\`, \`api/mcp.ts\`; новая ручка \`GET /api/egg-config\` выдаёт **только** URL нового Supabase и \`sb_publishable_...\`, если сервер корректно настроен. \`sb_secret_...\` не возвращается и не передаётся фронтенду.
- Auth: независимый \`SupabaseClient\` создаётся **только при открытии** панели серверного режима. Он **не использует** \`src/integrations/supabase/client.ts\` сайта.
- Данные: \`egg-engine-test\`, ref \`daluvgoonhgzomckxqnj\` (не Lovable).
- Сессия: email OTP / Supabase Auth; сервер всегда валидирует полученный bearer через Supabase \`auth.getUser\`, не доверяет его расшифровке браузером.
- Права: \`GET /api/egg?list=1\` возвращает первые 50 проектов **только подтверждённого owner_id**; внешнему агенту \`egg_v1_\` запрещено перечисление.
- Интерфейс: вкладка «Автор» → «Мои материалы · Google Drive» → «Сервер „Яйца“ · независимая база».

## Порядок использования

1. Автор отдельно открывает «Сервер „Яйца“» и вводит email. Нажатие «Отправить код» запрашивает email OTP в **новом** Supabase Auth; никаких паролей/токенов в ChatGPT.
2. Автор вводит полученный код. После успешной верификации клиент получает Supabase JWT сессии. Ранее сохранённые проекты этого Автора выбираются по зерну. Для других устройств тот же пользователь видит проекты в новой базе, а не через localStorage данного устройства.
3. Если серверного проекта с таким зерном нет, Автор явно нажимает «Создать серверный проект». Это новая запись в \`public.egg_engine_projects\`.
4. После создания читается состояние серверного проекта через \`GET /api/egg?projectId=...\`.
5. Локальные ссылки Drive НЕ отправляются автоматически. Напротив каждой выбираемой ссылки есть кнопка «Передать ссылку на сервер» → \`register_file\` с устойчивым \`operationId\`, повтор должен не плодить дубликаты.
6. Ссылка сохраняется как \`reported\`; только авторский \`confirm_file\` переводит её в \`author_confirmed\` **на сервере**.
7. Автор может повторно открыть панель (или войти на другом устройстве), увидеть собственный проект и его материалы. Локальная работа при недоступном API не теряется.

## Предварительные настройки Supabase Auth для email OTP

**Статус: пока НЕ проверено в настоящем браузере.**

Supabase штатно может отправлять magic link вместо видимого кода. Для входа по цифровому коду в [email template](https://supabase.com/dashboard/project/daluvgoonhgzomckxqnj/auth/templates) новой базы нужно включить **\`{{ .Token }}\`** в тело шаблона Magic Link/OTP. Не отправлять email-шаблон или код из личного письма в GitHub. Проверьте лимиты встроенной почты и авторизованный email. Согласно актуальным docs встроенный SMTP разрешает рассылку только подтверждённым адресам команды Supabase; для произвольных реальных пользователей нужен отдельный SMTP.

Для magic link необходимо настроить точный URL текущего **Preview deployment** в [Auth URL Configuration](https://supabase.com/dashboard/project/daluvgoonhgzomckxqnj/auth/url-configuration). Существующий сайт и его OAuth-параметры не использовать. Preview URL ещё должен быть опубликован.

## Проверки

- \`npm run egg:verify\` — 48 тестов успешно, 1 optional пилот пропущен. Vite build успешно. Server TypeScript \`api/egg.ts\`, \`api/mcp.ts\`, \`api/egg-config.ts\` компилируется.
- Тест \`EggAuthConfigEndpoint.test.ts\` подтверждает: без секретного ключа публичная конфигурация закрыта 503; при корректном серверном конфиге наружу выходит только publishable key.
- Тесты \`EggRemoteApi.test.ts\` проверяют браузерные вызовы и запрет выдавать агентский \`egg_v1_\` за пользовательский JWT.
- Не проверено пока: реальный email OTP, HTTP доступ после развёртывания, авторское создание/чтение в реальной базе, работа с разных устройств. Ни одной записи авторского проекта в новую базу этой разработкой не вносилось.

## Дальнейшее действие (один deliberate release)

После доступности Vercel deploy quota:
1. Запустить \`npm run egg:verify\` на точном commit SHA.
2. Один ручной Preview deployment той же ветки. Убедиться, что branch-scoped три \`EGG_SUPABASE_*\` доступны функции.
3. Настроить email OTP шаблон (и при необходимости auth redirect) только в новом Supabase.
4. Пройти реальный вход в Author UI, создать запись, прочитать и проверить через Supabase SQL, зарегистрировать тестовую Drive ссылку и подтвердить.
5. Проверить запрет доступа для неправильной/просроченной сессии и отсутствие серверных секретов в Vite bundle.

**Не менять production, Lovable Cloud, существующий сайт и хранение приватных документов.** Сквозной цикл — цель следующей проверки, а не уже подтверждённый факт.
