# Egg Engine v0.6 — пилот с настоящим Google Drive и безопасными повторами

**Статус (03.11.2026):** настоящая интеграция *с Google Drive со стороны подключённого ИИ* проверена. Интеграция *MCP ↔ живое серверное хранилище Яйца* пока не включена: соответствующей таблицы в Supabase нет, серверный секрет preview не настроен. Эта разница принципиальна.

## Что впервые удалось проверить на реальном объекте

1. Через подключённый Google Drive создан отдельный **приватный тестовый Google Doc** с минимальным техническим текстом. Подтверждено успешное создание и прочитан текст обратно через Google Docs; metadata показала \`shared=false\` и только owner permission. Сведения о реальном file ID передавались в тестовый процесс исключительно как переменная среды — **не помещены в GitHub**.
2. Изолированный тест \`src/test/EggConnectedDrivePilot.test.ts\` получил **реальные \`fileId\` и \`webUrl\`**, возвращённые Google. Он выполнил вызовы MCP JSON-RPC \`tools/call\`: чтение состояния → регистрация ссылки → повтор той же команды → экспорт манифеста.
3. Для проверки команд использовались **настоящие реализации** \`processEggMcp\`, \`runEggMutation\`, \`registerDriveReference\`, \`exportEggManifest\`, но **тестовая база в памяти**, а не HTTP-запрос к опубликованному MCP/реальный Supabase.
4. Результат: единственная запись со статусом \`reported\`, исходное зерно и история не изменились неожиданно, экспорт содержит ссылку без байтов файла. Повтор того же действия не создаёт дубликат. Имитация авторского подтверждения выполнялась только внутри unit test — пользователь не выполнял её на сервере.

## Идемпотентность при ненадёжном соединении

Внешний ИИ вызывает \`egg_register_drive_file\` с **operationId** — уникальным идентификатором *события сохранения*, а не содержимого файла.

- Первое действие вносит новую запись, увеличивает версию/ревизию.
- Если ответ потерялся, ИИ повторяет **тот же operationId с неизменёнными параметрами**. Движок отдаёт существующую запись, не создавая новую и не увеличивая счётчик.
- Если тот же operationId используется для другой ссылки, названия, группы или сферы — операция отклоняется.
- Новый реальный материал (или намеренно новая регистрация версии) использует **новый operationId**.
- При старой ревизии повтор с уже существующим идентификатором также распознаётся; новые операции продолжают требовать актуальную ревизию.

**Ограничение:** повтор с *другим* operationId всё ещё создаёт вторую запись. Проверка реальной Google revision и слияние файлов — отдельная задача.

## Возможность восстановить ссылки из JSON

В странице Автора появился элемент **«Восстановить ссылки из JSON»**. Он принимает \`egg.browser-bundle/0.1\` и \`egg.export/0.1\`, но не всякий произвольный JSON.

При импорте:
- проверяются исходное зерно, размер, формат, допустимость ссылок и идентификаторов;
- копируются **только Google Drive-ссылки**, назначение сферы и названия; дубликаты пропускаются;
- старый статус \`author_confirmed\` **не копируется**. Автор подтверждает возвращённый документ заново;
- исходное зерно, уровень, итерация, задачи, решения, содержимое файлов и изображения **не заменяются**.

То есть это **импорт реестра материалов**, не полный restore проекта и не доказательство серверной синхронизации.

## Что выяснилось о существующей инфраструктуре

Проверка инструмента Lovable подтвердила: **в проекте уже включён Supabase**. Но read-only запрос к \`information_schema\` показал, что таблицы \`egg_engine_*\` в \`public\` пока не установлены. Серверный endpoint без настроенных переменных секретов должен возвращать \`503 egg_engine_not_configured\`.

Из-за риска затронуть действующий сайт **никаких миграций в существующую production-базу не выполнялось**, разрешения к чужим проектам не расширялись, пользовательские Google-токены не копировались.

## Проверки

- Изолированный тест с реальным fileId из Google Drive + обычные регрессионные тесты.
- TypeScript для серверных модулей (\`api/mcp.ts\`, \`api/egg.ts\`, протокол) прошёл.
- Vite build прошёл.
- На общей TypeScript-компиляции репозитория остаются прежние три ошибки UNOcalc, не относящиеся к новому протоколу.
- **Не проверено:** работа MCP-клиента против реального Supabase, реальный вход Автора через страницу, запись в Google Drive из любых сторонних ИИ, Safari на iPad.

## Следующий действительно независимый этап

Нужен отдельный тестовый Supabase (либо явно разрешённая изолированная схема), где можно применить SQL v0.2. Затем:

1. Создать проект и ограниченный agent key через проверенную авторскую сессию.
2. Прочитать состояние проекта через публичный MCP endpoint.
3. Передать в него полученный Google Drive fileId.
4. В авторском UI открыть этот материал и подтвердить.
5. Отозвать ключ, повторить запрос, проверить отказ.

**Целевая архитектура не изменена:** человек остаётся в привычном ИИ, документы — в его Drive, методика/история — в Яйце. Реальный тестовый документ не публиковался публично.
