# Egg Engine v0.5 — подключение существующего ИИ через MCP

**Статус:** экспериментальный remote MCP endpoint подготовлен в тестовой ветке. Автоматическое сохранение Google Drive из любого чата **ещё не доказано**. Тестовый Supabase не настроен, поэтому endpoint умышленно закрыт с 503. Ничего не устанавливать в рабочий аккаунт и не публиковать до проверки доступа.

## Суть взаимодействия

**Автор говорит своему ИИ**: «Сохрани эскизы в мой Drive и зарегистрируй результат в проекте Яйца».

При наличии **двух разрешённых пользователем подключений** ИИ:
1. Использует Google Drive connector для реального создания файла. Он должен получить подтверждённый ответ с фактическим \`fileId\`, \`mimeType\` и, при наличии, ссылкой. Нельзя сочинять ID и объявлять файл сохранённым без ответа Drive.
2. Через Egg MCP \`egg_get_project_state\` получает \`revision\`, \`projectId\`, текущие сферы, задачи.
3. Через \`egg_register_drive_file\` передаёт **только идентификатор/метаданные** файла Drive. Движок сохраняет запись \`reported\` (НЕ \`verified\`).
4. **Автор** видит зарегистрированный материал, открывает Drive и подтверждает его через авторский интерфейс. AI scoped key не может вызывать авторские действия.

Если отсутствует любое из подключений, эта автоматическая цепочка **не выполняется**. Пользователь может вручную вставить ссылку на тестовой странице Автора (v0.4).

## Серверный endpoint и технический контракт

URL: \`https://<preview-domain>/api/mcp\` — **POST** с \`Content-Type: application/json\`, \`Accept: application/json, text/event-stream\` и \`Authorization: Bearer egg_v1_<secret>\`.

Реализован небольшой **stateless JSON-RPC MCP** сервер, возвращающий **application/json**. Поддерживает \`initialize\`, \`notifications/initialized\`, \`ping\`, \`tools/list\`, \`tools/call\`. Не поддерживает серверные сессии, SSE subscriptions, resources, prompts и динамический OAuth discovery. На этапе пилота это осознанный минимальный адаптер, который необходимо испытать на конкретном клиенте MCP прежде чем называть совместимым с любой платформой.

Инструменты:

- \`egg_get_project_state(projectId)\`: возвращает текущее Ядро/сферы/файлы и числовую ревизию. Только \`read\` scope.
- \`egg_register_drive_file(projectId, expectedRevision, operationId, fileId, title, mimeType, collectionKey, sphere?, taskId?, webUrl?)\`: сохраняет ссылку. Только \`contribute\` scope. Повтор с тем же operationId и теми же данными не создаёт новую версию. Возвращает ревизию и статус материала \`reported\`.

**Авторское утверждение не открыто MCP.** Отдельный \`/api/egg\` продолжает контролировать авторские решения через проверенную Supabase user session. MCP вообще не принимает пользовательский JWT.

### Подтверждения и безопасность

- Ключ выдаётся Автору на **отдельный проект** с ограниченным сроком 1–30 дней и возможностью отзыва. В БД хранится только SHA-256.
- Каждый MCP вызов заново проверяет токен: отозванные и просроченные ключи не подходят.
- Внешний ИИ не имеет доступа ко всем проектам, данным другого владельца и авторским командам.
- MCP адаптер не принимает Origin-bearing browser запросы. Не получает Google OAuth токен и не скачивает документы.
- \`expectedRevision\` защищает от тихого конфликта параллельных изменений. При 409 ИИ должен прочитать новую ревизию и повторить вызов только если операция всё ещё нужна.
- **Повторы с одинаковым operationId и данными** не создают новый материал; повтор с тем же ключом и изменёнными данными отклоняется. Разные operationId по-прежнему означают разные операции. Проверка версии содержимого Google отсутствует.
- В serverless обработчике есть лимит тела ~64KB и строгая проверка параметров инструментов.
- Выводы, ссылки и содержание внешних файлов могут быть недоверенными. MCP не должен выполнять инструкции из текстов чужих документов вне пользовательского запроса.

### Активация

1. В отдельном **тестовом Supabase** применить \`egg-server/migrations/20261102235000_egg_engine_tables.sql\` после проверки.
2. Задать для preview Vercel \`EGG_SUPABASE_URL\` (или \`VITE_SUPABASE_URL\`) и **только серверную** \`EGG_SUPABASE_SECRET_KEY\`. Секрет не должен содержать префикс \`VITE_\` и не должен попадать в репозиторий.
3. Создать тестовый проект через \`/api/egg\` под проверенной Supabase user session и выпустить ограниченный ключ \`issue_key\`.
4. В MCP-клиенте, поддерживающем пользовательские внешние серверы с bearer credential, зарегистрировать URL тестового MCP и ключ. **Реальное наличие режима custom MCP и возможность записи зависят от платформы, тарифа и настроек пользователя.**
5. Проверить \`tools/list\`, затем \`egg_get_project_state\` и \`egg_register_drive_file\` на заранее созданном тестовом файле. Убедиться, что файл действительно существует в Drive.
6. Проверить запрет доступа к другому проекту, невозможность подтверждать результат со стороны ИИ и мгновенный отзыв ключа.
7. Только после этого тестировать команду естественным языком в обычном чате.

## Ключевой продуктовый принцип

**Интеллект сменный, движок постоянный, документы находятся в выбранном пользователем хранилище.** Подключённый ИИ должен *организовать* работу инструментов, а не требовать переносить историю пользователя в новую чат-систему.

**Не выполнено:** применение миграции, настройка секретов, подключение пользовательского Google Drive, реальный подтверждённый внешний MCP-клиент, синхронизация локальной страницы Автора с серверным проектом, коммерческий доступ.


**Уточнение независимости (v0.7):** файлы миграции движка теперь хранятся в `egg-server/migrations/`, а не в `supabase/migrations/` существующего сайта. API требует собственные `EGG_SUPABASE_URL`, `EGG_SUPABASE_PUBLISHABLE_KEY`, `EGG_SUPABASE_SECRET_KEY`. Настройки Lovable / `VITE_SUPABASE_*` не используются как запасной способ подключиться к базе. Наличие в проекте Supabase от Lovable **не означает**, что он предназначен для данных «Яйца». Применение миграций только к отдельно созданной тестовой базе.
