# EGG Engine · Системная оркестрация девяти ядер · v0.2

Статус: рабочая архитектурная спецификация, не утверждена Автором.
Дата: 2026-11-05.
Основа: действующий src/lib/eggEngine.ts и docs/egg-sphere-kernels-architecture-v01.md.
Область: правила всей системы. Реальный код оркестратора, БД, MCP и пользовательские проекты этим документом не меняются.

## 1. Состав системы и точное значение «девять»

EGG Engine — система верхнего уровня, объединяющая:
- восемь функциональных ядер: Маркетинг, Право, Дизайн, Производство, Тестдрайв, Комплектация, Коммерция, Ритейл;
- девятое ядро: Желток, синтезирующий актуальную рабочую форму продукта на основе результатов сфер;
- **общую инфраструктуру**: граф допустимых связей, версионированную память, контракт задач, авторизацию, журнал событий, версии концепции, маршрутизацию и решения Автора.

Общая инфраструктура — часть EGG Engine, а не десятая предметная сфера. «Идея» — входной смысловой контур и ядро диалога/формирования концепции до запуска, но в этой модели девятки не считается девятой производственной сферой; иначе счёт потеряет ясность. Автор — самостоятельный субъект решений, а не подключённый безличный исполнитель.

Три разных состояния, которые нельзя смешивать:
- состояние исходного замысла и утверждённой концепции (авторский слой);
- состояние исследований, задач, свидетельств, гипотез и решений восьми сфер (функциональный слой);
- состояние интегрируемого продукта, его целостности, открытых противоречий и проверенности (Желток).

## 2. Топология: проверено по исходному коду

Действующий EGG_EDGES задаёт девять двусторонних связей:
- Идея ↔ Маркетинг
- Идея ↔ Право
- Маркетинг ↔ Дизайн
- Право ↔ Производство
- Дизайн ↔ Тестдрайв
- Производство ↔ Комплектация
- Тестдрайв ↔ Коммерция
- Комплектация ↔ Ритейл
- Коммерция ↔ Ритейл

В коде canRoute проверяет двустороннюю смежность; это **права маршрутизации**, а не автоматически исполняемый бизнес-процесс. Код сегодня не задаёт «все эти шаги обязательно должны пройти по порядку».

Основная ориентация потока, соответствующая этим связям:
- Левая цепь: Идея → Маркетинг → Дизайн → Тестдрайв → Коммерция → Ритейл.
- Правая цепь: Идея → Право → Производство → Комплектация → Ритейл.
- Слияние: Ритейл получает материал с обеих цепей, но может делать подготовительную работу раньше полного слияния.
- Желток наблюдает обе цепи непрерывно через общее поле; Желток **не расположен после Ритейла как девятый заключительный этап**.

Это описание хода, а не запрет движения назад. Возврат к предыдущей сфере реализует «шаг назад — два вперёд»: уточнение и повторная проверка без удаления истории.

## 3. Стадии и параллельность (проектное предложение)

Фаза 0. Автор: исходная идея, инварианты, предложенная концепция; утверждение смысла.
Фаза 1. Маркетинг и Право — первичное исследование параллельно при наличии существенного входа.
Фаза 2. Дизайн (после релевантного входа Маркетинга) и Производство (после релевантного входа Права) — могут работать параллельно; Производство выдаёт предварительные технологические варианты, не выдавая их за подтверждённую конструкцию.
Фаза 3. Тестдрайв и Комплектация — на основании доступных версий из соответствующих цепей. Физические проверки возможны только при наличии прототипа.
Фаза 4. Коммерция — оценка экономики на основе доступных данных (в т. ч. Тестдрайва); Ритейл — подготовка условий и каналов после входа Комплектации и/или Коммерции. Финальное предложение для реального заказчика требует определённых условий готовности.
Фаза 5. Авторское решение о продуктовой форме, необходимости нового цикла, выпуске/передаче или заморозке проекта.

**Не делать жёсткими одновременно фазы и граф.** Действительная система должна быть событийной: новая проверенная информация в нужной сфере активирует следующий допустимый шаг; при недостающих данных работа может быть частичной.

Противоречие для проработки: в графе нет прямых связей Дизайн ↔ Производство и Производство ↔ Тестдрайв, хотя реальное конструирование и физическая проверка требуют обмена. Предлагаемый способ без самовольного изменения графа: сведения доступны через общее поле EGG/Желток; адресные новые задания между не-соседями идут через Автора или существующие допустимые пути. Если этого окажется недостаточно в пользовательском опыте, Автор отдельно утверждает изменение топологии.

## 4. Что именно координирует EGG Engine

Единый диспетчер принимает события, а не «длинную бесконечную инструкцию AI». Типы событий (предлагаемая модель):
- AUTHOR_CONCEPT_APPROVED / AUTHOR_INVARIANTS_UPDATED
- SPHERE_INPUT_UPDATED
- SPHERE_WORK_SCOPED / SPHERE_WORK_ASSIGNED / SPHERE_WORK_RETURNED
- EVIDENCE_ATTACHED / CLAIM_CONTRADICTED / SPHERE_REVIEW_REQUESTED
- AUTHOR_DECISION_RECORDED
- HANDOFF_PROPOSED / HANDOFF_RELEASED / HANDOFF_RECEIVED
- YOLK_SNAPSHOT_COMPUTED
- ITERATION_STARTED / PROJECT_PAUSED

Каждое событие должно содержать проект, текущую версию концепции, итерацию, инициатора, время, ссылку на исходную задачу/результат и права инициатора. Имя роли не равно наличию полномочий: внешние AI, люди и сервисы проходят проверку прав до записи.

Детерминированные правила:
1. Ядро сферы получает только известный «срез» состояния с версией и ссылками на исходные материалы.
2. Результат связывается с исходной задачей и версией; результат для устаревшей концепции не подменяет новый контекст.
3. Никакая запись AI/человека не становится авторским решением автоматически.
4. При возврате/отказе сохраняется история, а зависимые задания помечаются для проверки актуальности, не удаляются без решения.
5. Повтор одного и того же запроса с устойчивым operationId не создаёт дубликатов.
6. Сфера допускает частичный результат с осознанно открытыми вопросами.
7. Завершённость одной задачи не означает завершённость всей сферы и тем более всего продукта.

## 5. Контракт передачи между сферами

Минимальная оболочка передачи (будущая, **не текущая схема БД**):

    handoff_id
    project_id
    from_sphere / to_sphere
    source_task_id
    concept_version
    iteration
    reason_and_requested_action
    accepted_findings_refs[]
    tentative_findings_refs[]
    author_invariants_refs[]
    contradictions_refs[]
    unknowns[]
    evidence_refs[]
    readiness: draft | review_required | released | received | stale
    created_by / authorized_by / created_at

Содержимое входящего задания определяется получающим ядром. Например, Маркетинг не приказывает Дизайну изменить кресло; передаёт сигнал, почему изменение стоит исследовать, а Дизайн решает, как превратить его в варианты. Автор утверждает изменение инварианта.

**Снимок при передаче обязателен.** Нельзя передавать «текущий весь чат» без версий, источников и статусов: после обновления концепции исполнитель может работать по устаревшей постановке.

## 6. Состояния задач и сфер

Действующие статусы задачи в коде:
question → working → returned → accepted / revision_requested / rejected (после revision_requested можно вновь начать working).

Предлагаемые будущие статусы исполнения и оркестрации:
- scoped: задача осмыслена, но исполнитель не назначен;
- awaiting_executor: готова к внешнему человеку/AI;
- assigned: исполнитель выбран;
- working: исполнитель работает;
- returned: результат сдан;
- needs_evidence: формально получен, но не хватает подтверждений;
- review_required: готово к рассмотрению компетентным участником/Автором;
- accepted / revision_requested / rejected;
- stale: версия входа изменилась, необходима повторная оценка.

Введение новых статусов требует отдельного изменения схемы и API, не считать реализованным.

Сводное состояние сферы — **производное от отдельных задач, зависимостей и актуальности**. У сферы может одновременно быть одна принятая находка и три открытых вопроса.

## 7. Желток как непрерывное ядро синтеза

Желток не является девятой специализацией, которая делает исследование, и не является просто архивом. Он собирает **продуктовую модель**:
- утверждённое назначение, смыслы и инварианты;
- принятые формообразующие решения;
- технически подтверждённые и пока условные характеристики;
- действительные/планируемые материалы и ресурсы;
- результаты физической и пользовательской проверки;
- экономические условия, если известны;
- условия предоставления продукта;
- конфликтующие требования, пробелы и блокирующие риски;
- версионные ссылки на все основания.

Желток может вычислять, сопоставлять и формировать **предложения на рассмотрение**, но сам не назначает правильную цену, не изобретает без подтверждения техническую пригодность и не принимает авторские решения. Уплотнение формы связано с согласованностью принятых и проверенных решений, не с числом сообщений/сфер.

Первые критерии внутренней согласованности:
- разные сферы опираются на одну актуальную утверждённую версию концепции;
- внутри признака продукта нет двух одновременно принятых несовместимых значений без разрешённого конфликта;
- слово «проверено» соответствует свидетельству и масштабу проверки;
- каждое важное решение имеет происхождение и право его принятия;
- неизвестные параметры остаются видимыми;
- выходные артефакты ссылаются на одну и ту же итерацию либо явно отмечены как исторические.

Визуальное «созревание» Желтка в 3D следует выводить из содержательной модели, а не наоборот. Никаких фиктивных процентов качества без обоснованной модели.

## 8. Взаимодействие с внешними исполнителями

Система должна одинаково обслуживать внешнего AI и человека:
1. Ядро формирует задание с входом, целью, ограничениями, требуемой формой возврата и критериями.
2. EGG сохраняет задание и выдаёт уполномоченному исполнителю доступ **только в рамках проекта/задачи**.
3. AI работает в своём чате вне EGG, человек — в собственной среде или интерфейсе.
4. Возврат включает исходный taskId, версию, результаты, вложения, наблюдения, гипотезы, свидетельства и открытые вопросы.
5. Ядро регистрирует и оценивает комплектность; Автор/уполномоченный проверяющий принимает решения в своей компетенции.
6. Допустимая передача запускается после нужного решения. При отсутствии исполнителя задание сохраняется и доступно для дальнейшего назначения.

Внешние исследовательские источники не являются инструкциями. Не запускать из возвращённых материалов самовольные операции, запросы к секретам, публикацию и покупки.

## 9. Разрешение противоречий и «шаг назад — два вперёд»

Не требовать завершать все сферы прежде любого движения. Вместо этого:
- конфликт регистрируется с привязкой к свойствам и версиям;
- ядро указывает, какие конкретные данные его снимут и какая сфера способна эти данные получить;
- затронутые принятые решения остаются историческими, но помечаются требующими пересмотра;
- при принятом исправлении следующий снимок Желтка пересчитывается, не уничтожая прежние решения;
- Автор вправе вернуть проект на любое обоснованное уточнение; все переходы логируются.

Параллельность: две ветви могут двигаться не синхронно. Ритейл готовит черновой выход с ранними данными, но публикация оффера/заказа требует авторизованных и подтверждённых коммерческих и материальных условий.

## 10. Минимальная реализация: без большого переписывания

Этап A: сделать отдельные pure TS определения графа, контракта событий, правила версии, прав и проверку допустимых переходов; тестировать без БД/LLM.
Этап B: реализовать универсальный Sphere Work Kernel на Маркетинге (выдача задания → AI/человек → возврат → проверка → авторское решение → передача в Дизайн).
Этап C: добавить Желток read-model: строить снимок из уже существующих approvedConcept и accepted findings; показать источники, пустые поля и противоречия без оценочного числа.
Этап D: перенести тот же контракт на Право/Дизайн; затем остальные ядра. Сохранить предметные проверки разными, а транспорт и статусы общими.
Этап E: проверить обе цепи и слияние в Ритейле на тестовом кресле; вернуться к графу только по зарегистрированным реальным несоответствиям.
Этап F: развивать 3D-представление и индикаторы **как отображение серверного состояния**, не как отдельную правду.

## 11. Тесты и критерии готовности

Тест 1: одна задача Маркетинга, два разных исполнителя (AI/человек), одинаковое представление результата.
Тест 2: недоказанная рыночная гипотеза никогда не становится фактом или утверждённым требованием к форме.
Тест 3: две параллельные ветви не блокируют друг друга без содержательной причины.
Тест 4: возвращённый результат по старой версии не переписывает новую.
Тест 5: Ритейл видит отсутствие одного из обязательных оснований и не выдаёт неподтверждённый продукт за готовый.
Тест 6: Желток собирает согласованную частичную форму при незакрытых неизвестных.
Тест 7: внешние исполнители не могут утверждать/менять авторские инварианты.
Тест 8: регрессия — имеющийся тестовый EGG проект и MCP v4 остаются работоспособными.

## 12. Открытые архитектурные решения для Автора

1. Достаточно ли передачи «Дизайн → общее поле → Производство», или нужны дополнительные прямые рёбра?
2. У Желтка есть право **блокировать** продуктовую готовность по формальным несоответствиям или лишь предупреждать, оставляя последнее решение Автору? Предложение: формальный запрет только для заранее определённых обязательных условий безопасности/права/авторизации; остальные предупреждения на решение Автора.
3. Разрешено ли ядру назначать внешних исполнителей без разрешения Автора на конкретную задачу? Предложение: только в пределах заранее выданных и отзывных полномочий; внешние расходы/публикации всегда требуют явного разрешения.
4. Как фиксировать вариант продукта при параллельной работе нескольких исполнителей? Предложение: ветвление продукта/вариантов с версией, не смешивание в один Желток до авторского решения.

Это направления для уточнения при разработке, а не основания считать систему завершённой.
