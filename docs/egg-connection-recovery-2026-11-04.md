# EGG · Восстановление соединения ChatGPT ↔ EGG (04.11.2026)

## Симптом

Встроенный EGG v3 коннектор ChatGPT возвращал `The deployment has been removed` для `egg_get_project_state` и `egg_register_drive_file`. Одновременно preview-ветка `prototype/chat-ai-handoff` показывала работающую страницу, но её `/api/egg-config` отвечал `503 egg_engine_not_configured`, тогда как `/api/mcp-health` ошибочно сообщал `ok:true` (он проверял лишь локальный протокол).

## Две отдельные причины

1. MCP коннектор ChatGPT был связан со старой веточной ссылкой на deployment Vercel, который более не был доступен. Ссылка настроек EGG: `https://project-a4e09c64-fce9-40-git-e8febd-kolesnikovuno-jpgs-projects.vercel.app/api/mcp`.
2. Четыре переменные EGG Supabase и MCP origin настроены **только** на preview Git-ветке `prototype/design-brief-sketch-gates`. Новая непроизводственная ветка `prototype/chat-ai-handoff` не получила эти переменные. Это правильное ограничение доступа к секретам, его нельзя «исправлять» копированием ключей в код или ко всем PR-превью.

## Восстановление

- Сверено, что `prototype/design-brief-sketch-gates` — предок разработческой ветки без конфликтов (0 коммитов отставания).
- PR #2 объединил код на **настроенной** preview-ветке; основная `main` и рабочий сайт не изменялись.
- Новый Vercel preview той же ветки восстановил прежний стабильный адрес веточного алиаса.
- `/api/egg-config` вернул HTTP 200 и валидную публичную конфигурацию.
- `/api/mcp-health` проверен, но локальная проверка инструментария не гарантирует доступа к проекту или OAuth.
- Исполненный из ChatGPT `egg_get_project_state` для `01b3d29f-bfc4-41ed-b31a-2e0db7fa2fe9` снова вернул состояние ревизии 11.
- Настоящий Google Doc с ID `1tzhlvD1-e9T-FROIOiGa4DMu-19BiYYn48UQq7acxxM` зарегистрирован через **EGG MCP** с устойчивым `operationId=idea-A-embrace-concept-v1-doc-20261104`, получил ID `artifact-11`, статус `reported`. Повторное чтение подтвердило проектную ревизию **12** и наличие артефакта.
- В UI сферы «Идея» добавлена авторская регистрация и отдельное подтверждение ссылок на Google Документы; она использует JWT пользователя, существующие `register_file` / `confirm_file` через `/api/egg`. Это резервный путь, если ChatGPT коннектор снова недоступен.
- `/api/mcp-health` дополнительно требует корректную конфигурацию EGG Storage и возвращает HTTP 503 при её отсутствии. Не считать это полноценным тестом OAuth.

## Критичные границы

- Текущий документ — **ссылка на файл**, он не становится автоматически утверждённой концепцией в EGG Engine Core. Он имеет статус `reported`, а не `author_confirmed`.
- Концепция A в Google Doc остаётся **на утверждение**. Отдельные `propose_concept` и `decide_concept` производятся через UI Автором/подключённым клиентом; AI самостоятельно ничего не принимает.
- В установленном ChatGPT коннекторе EGG v3 может отсутствовать `egg_propose_concept`, даже если backend `/api/mcp-health` уже перечисляет его в своих средствах. Нельзя заявлять, что этот инструмент доступен ассистенту, пока он не появился в инструментарии ChatGPT.
- Нельзя переносить секретный `EGG_SUPABASE_SECRET_KEY` в preview-код, браузер, логи, chat, GitHub или общий Preview target.
- Если старый deployment удалён, реальный путь восстановления — deployment **на той же настроенной ветке** и проверка сквозной операции, а не только успешная сборка/Vite UI.

## Быстрая диагностика при повторении

1. Vercel: активное развертывание ветки `prototype/design-brief-sketch-gates`, состояние READY, алиас `...-git-e8febd-...vercel.app`.
2. GET по `/api/egg-config`: HTTP 200 и `ok:true` (публичную publishable-конфигурацию разрешено передавать клиенту; service key — никогда).
3. GET по `/api/mcp-health`: HTTP 200, `checks.protocol:true`, `checks.storageConfigured:true`.
4. Реальное чтение через подключённый EGG `egg_get_project_state` должно вернуть актуальную ревизию тестового проекта. Никаких побочных изменений при чтении.
5. При восстановлении регистрации файлов повторять с прежним `operationId`, прежде проверив наличие файла в текущем состоянии (идемпотентность).
