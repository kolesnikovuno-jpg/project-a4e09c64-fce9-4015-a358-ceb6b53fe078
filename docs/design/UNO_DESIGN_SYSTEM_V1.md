# UNO Design System v1 — рабочая спецификация

**Статус:** v1 / техническое внедрение начато; внешний вид действующего интерфейса не меняем.  
**Проект:** kolesnikov.studio (единый GitHub/Vercel проект).  
**Дата аудита:** 2026-11-19.  
**Эталоны:** текущая главная (`src/pages/site/Landing.tsx` / `Landing.css`) и LYRA (`src/pages/Lyra.tsx`, `src/components/LyraInfo.tsx`, `LyraRequestPanel.tsx`).  
**Назначение:** сохранить индивидуальность страниц, но устранить непреднамеренные расхождения в шрифтах, ритме, навигации и панелях.

## 1. Принцип

**Одна студия, три режима интерфейса:**

1. **Автор / экспозиция:** пространственная типографика, свободная композиция, сознательно нестандартный масштаб и обрезка. Примеры: главная, LYRA, NAVA.
2. **Чтение / объяснение:** читаемая типографика и устойчивая вертикальная иерархия. Примеры: Studio, Clarity, About.
3. **Документ / управление:** моноширинная система для технических характеристик, форм, статусов, панелей и операторских данных.

Это функциональные роли, **не три несвязанных дизайна**. Общими остаются палитра, качество линий, логика состояний, доступность и спокойное поведение.

**Ещё одно наблюдение:** декларации `@font-face` Medeo Sans в `src/index.css` указывают на служебные asset URL вида `/__l5e/assets-v1/...`; перед рефакторингом стоит подтвердить загрузку на production и корректность переноса в обычные локальные assets.

## 3. Предложение: типографическая система (to-be)

| Роль | Семейство | Начертание | Предлагаемый диапазон | Tracking | Применение |
| --- | --- | --- | --- | --- | --- |
| Display / архитектурный жест | Medeo Sans | 300–400 | адаптивный, вне общей шкалы | индивидуально, допустима экстремальная разрядка | экспозиция, имена, композиционная типографика |
| H1 / смысловой заголовок | Medeo Sans | 300–400 | 28–44px | 0…0.02em | заголовки страниц чтения |
| H2 / секция | Medeo Sans | 300–400 | 20–28px | 0…0.04em | структурные разделы |
| Body / содержание | Medeo Sans | 300–400 | 15–16px | 0…0.04em | абзацы, пояснения |
| Caption / подпись | Medeo Sans | 300–400 | 11–13px | 0.10…0.22em | метки, интерфейсные аннотации |
| Technical / документ | один явно поставляемый monospace (пока кандидат, не утверждён) | 400 | 11–12.5px | 0.01…0.08em | INFO, Request, характеристики, статусы |
| Technical title | тот же monospace | 400 | 28–34px | ~0.04em | заголовок панели документа |

**Важное исключение:** значения для display-главной, включая `kolesnikov.studio`, сверхкрупный EGG и верхний ряд, **не нормализовать** под текстовую шкалу. Это осознанные авторские формы.

**Мобильный принцип:** не переносить десктопные размеры механическим уменьшением; сохранять читаемость и переносы. Технический текст и поля ввода проверять отдельно на touch-устройствах.

## 4. Цвета и линии

Исходная палитра (уже присутствует):

- `canvas`: HSL 24 26% 94% (≈ #F5EFEB, зависит от точного округления);
- `ink`: HSL 0 0% 20%;
- `accent`: HSL 203 24% 45%;
- документальная панель: `#F5EFEB`;
- документальный основной текст: `#3A3A3A`, сильный `#1F1F1F`, метаданные `#8A8A8A`, слабый `#9A9A9A`.

Предлагаемое правило: **цвета через смысловые токены**, а не через разные шестнадцатеричные константы в каждом компоненте. Сохранить низкую насыщенность и возможность контролируемого акцента; не вводить яркие цветные плашки без функциональной причины.

Разделители:

- технический документ: тонкая пунктирная линия, пример INFO `1px dashed rgba(0,0,0,.18)`;
- структурная страница: тонкая спокойная сплошная линия;
- экспозиционная страница: линия только там, где имеет функциональный смысл.

## 5. Компоненты — будущие контракты

| Компонент | Общие правила | Сохраняем индивидуальность |
| --- | --- | --- |
| `DocumentPanel` | ширина, padding, slide, backdrop, закрытие, ESC, фон, мобильный full-width | состав документа и информационные блоки |
| `DocumentMeta` | служебный ref / дата | фактические данные |
| `DocumentHeading` | технический шрифт, размер, вес | заголовок |
| `SectionLabel` | 10px, разреженный uppercase, префикс `//` | текст раздела |
| `DocumentRule` | пунктирный разделитель | толщина для отдельных этапов |
| `DocumentField` | подпись, тонкая линия, focus-visible, сообщения об ошибках | бизнес-валидация |
| `QuietAction` | действие как текстовая строка, hover/focus | переход или отправка |
| `ProjectNavigation` | размеры, вес, состояние hover/focus | набор ссылок, композиция |
| `ReadingLayout` | контентная ширина, отступы, масштаб заголовков | ритм конкретного текста |

**Поведение:** компоненты описывают визуальный контракт, не заменяют бизнес-логику. Форму LYRA и её сохранение данных в Supabase нельзя изменять попутно с типографикой.

**Доступность:** видимый keyboard focus, семантические кнопки и ссылки, читаемые контрасты, `prefers-reduced-motion`, адаптивное размещение. Пониженный контраст допустим для декора, но не для ключевых текстов и полей.

## 6. Карта разделов и разрывов

| Зона | Состояние | Приоритет | Следующее действие |
| --- | --- | --- | --- |
| Главная | текущий авторский эталон | P0 / freeze | не трогать; только документировать пропорции |
| LYRA / INFO / Request | документальный эталон и действующая форма | P0 / freeze | извлечь токены; затем без изменения поведения создать shared panel |
| NAVA / INFO | близкий родственник LYRA | P1 | сравнить 1:1, убрать только непреднамеренные расхождения |
| Studio / Method / Cases / Exchange / Start | частично единые локальные классы | P1 | перенести локальную шкалу в общие токены после визуального сравнения |
| Clarity / Intake | самостоятельная информационная и форма-зона | P1 | привести заголовки, подписи полей, разделители и состояния |
| Semantic Time | самостоятельная продуктовая композиция | P2 | сохранить цифры и интерактивный характер; унифицировать только служебный текст |
| EGG Gate / UNOcalc / Lab | продуктовые и технические экраны | P2 | стандартизировать поля, подписи и управляющие элементы, не форму продукта |
| Operator | рабочий бэкофис | P2 | наследовать документальный режим; учитывать плотность данных |
| About / Garden / Pricing / прочее | содержание и каталог | P2 | проверить по режиму чтения и общей навигации |

**Граница аудита:** это карта по исходникам, а не полноценный визуальный QA на реальных разрешениях. Приоритеты — проектное предложение, не измеренные пользовательские проблемы.

## 8. Правила изменений

1. **As-is / to-be разделяются:** факт, гипотеза, решение.
2. Для каждого изменения: затронутые компоненты, причина, ожидаемое визуальное поведение, откат.
3. Деплой для визуальных изменений обязателен, когда пользователь сравнивает реальные композиции; документы и внутренние refactor-задачи не должны расходовать цикл без причины.
4. Существующие функции и ссылки нельзя менять при стилистической настройке.
5. Главная и LYRA — защищённые эталоны до отдельного решения об изменении.
