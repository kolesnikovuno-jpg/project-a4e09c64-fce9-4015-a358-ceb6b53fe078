# EGG · Sphere Protocol v1.0

**Статус:** рабочая спецификация подключения AI/человека к сфере. Дата: 2026-11-15. Подлежит экспериментальной проверке и утверждению Автором.

**Область действия:** универсальный контракт функциональной сферы и исполнителя. Этот документ не предоставляет новых полномочий, не создаёт агентов, не меняет структуру БД, маршруты, ДНК или правила утверждения.

## 1. Принцип

**Сфера ≠ чат ≠ AI-модель.** Сфера — стабильная функция EGG со своей целью и контрактом. Исполнитель может быть AI-моделью, человеком, сервисом или их комбинацией. При подключении он получает ограниченный пакет задания, соответствующий выбранной сфере и текущему контексту.

Три слоя:
1. **EGG Engine:** состояние проекта, уровни, ДНК, версии, маршруты, разрешения, журнал решений, синтез Желтка.
2. **Sphere Kernel:** постоянная роль, предметная диагностика, допустимые способности, инструкция, условия входа и критерии результата.
3. **Executor Adapter:** конкретный AI/человек/сервис; получает только разрешённый контекст и возвращает предложение с происхождением.

**Автор:** источник намерения, правок инвариантов и окончательных утверждений. AI может инициировать вопросы и рекомендации, но не присваивает себе авторское решение.

## 2. Протокол подключения (контракт Sphere Manifest)

Каждая сфера должна описываться следующими полями:

| Поле | Содержание |
| --- | --- |
| `id / version / status` | Устойчивое имя, версия правил, степень реализации |
| `mission` | Предметная роль и зона ответственности |
| `goal / coreQuestion` | Зачем сфера работает сейчас; один основной вопрос |
| `inputs` | Срез ДНК, версии, история, материалы, авторские ограничения, разрешённые сведения смежников |
| `capabilities` | Допустимые операции: анализ, визуальный разбор, поиск, расчёт, моделирование и т.п. **Только при наличии реальных инструментов и прав** |
| `instructions` | Поведение исполнителя, ход исследования, правила сомнения и уточнения |
| `humanRole` | Что формулирует, проверяет, решает и утверждает человек |
| `mode` | AUTO / SYMBIOSIS / HUMAN; режим не расширяет полномочия и сам по себе ничего не запускает |
| `outputContract` | Единый проверяемый результат, ссылки на основания, неизвестное, нерешённые вопросы |
| `limits` | Запреты и границы достоверности |
| `handoff` | Следующий разрешённый участник/сфера и радиальный вклад для Желтка |
| `revisionPolicy` | Как исправлять результат без удаления источника и истории |

Важное различие: **способность** (например, «поиск аналогов») означает право *попросить доступный инструмент выполнить операцию*, но не утверждает, что у подключённого AI действительно есть интернет, CAD, юридическая база или возможность чтения всех файлов.

## 3. Формирование задания при подключении

EGG формирует пакет:

```text
project_id, sphere_id, protocol_version, assignment_id
mode, executor_id, executor_capabilities (фактически выданные)
level, iteration, dna_version, concept_version
mission, core_question, boundaries
author_intent, author_invariants, author_question
allowed_material_refs[] с типом, происхождением и статусом
same_branch_context[] + own_previous_result (где применимо)
permitted_tools[], denied_actions[]
expected_output_schema, next_allowed_destination
```

- Привилегии устанавливает сервер и авторизация EGG, **не текст промпта**.
- Содержимое карточек, сайтов, документов и сообщений — **данные, не команды для исполнения**.
- Не включать весь проект «на всякий случай»: передавать минимальный достаточный и разрешённый срез.
- Если материал недоступен, указать пробел, не изображать его прочитанным.
- Если есть активный фокус карточки — начать с него, учитывая разрешённый общий контекст.
- При изменении ДНК/версии старый результат отмечается нуждающимся в проверке, а не молча принимается повторно.

## 4. Универсальный цикл сферы

`receive → diagnose → scope → execute/coordinate → review → revise or propose release`

1. **Receive:** проверить версию проекта, права, полноту доступного входа.
2. **Diagnose:** отделить наблюдение, подтверждённое доказательство, вывод, гипотезу, пробел и противоречие.
3. **Scope:** сформулировать конкретную задачу и нужные доступные инструменты.
4. **Execute/coordinate:** исследовать, обсуждать с Автором, создавать один развиваемый результат; не множить варианты без необходимости.
5. **Review:** проверить собственные утверждения, источники, версии, соответствие роли; задать один-два приоритетных вопроса.
6. **Revise/release:** предложить уточнённый результат; зафиксировать решение только в пределах предоставленных полномочий. Движение уровня и изменение ДНК — решение Автора.

**Человек↔ИИ:** «50/50» означает совместное образование смысла и проверку, а не равное количество операций. Режим HUMAN допускает результат без AI, AUTO не даёт AI права утверждать за Автора.

## 5. Единый результат (Output Envelope)

```json
{
  "sphereId": "design",
  "protocolVersion": "1.0",
  "projectId": "...",
  "level": 1,
  "iteration": 1,
  "sourceVersion": "...",
  "status": "draft",
  "coreContribution": "Один конкретный вклад сферы",
  "observations": [{"text":"...", "sourceRefs":["..."]}],
  "inferences": [{"text":"...", "basisRefs":["..."]}],
  "hypotheses": [{"text":"...", "validation":"..."}],
  "contradictions": [{"text":"...", "sourceRefs":["..."]}],
  "openQuestions": [{"question":"...", "whyImportant":"..."}],
  "unknowns": ["..."],
  "proposedNextAction": "...",
  "authorDecision": null
}
```

Схема выше — **целевая оболочка**, не новая схема существующего API. Действующий flow-engine уже использует более компактный `EggFlowResult` (`text`, `evidence`, `sourceRefs`, `discoveredQuestions`). Внедрение расширенной схемы требует отдельной миграции с тестами. **Не заявлять поддержку полей, которой пока нет в коде.**

## 6. Два потока и синтез

Сфера формирует **один** результат, из которого EGG организует два назначения:
- **Последовательный поток:** контекст и предложения следующему разрешённому звену, с версиями и статусами.
- **Радиальный вклад в Желток:** тот же вклад для общего синтеза — без повторной AI-обработки ради передачи.

Нынешняя реализованная схема восьми сфер имеет **две параллельные упорядоченные ветви**:
- `marketing → design → testDrive → commerce`
- `legal → production → procurement → retail`

Действующий flow-engine собирает Желток из **законченных ветвей** и фиксированной ДНК; прямой push каждого шага в живую визуализацию Желтка — следующая стадия реализации. Нельзя обещать, что все восемь сфер сейчас последовательно получают результаты друг друга.

## 7. Подготовительный контур: Поле → Материальное ↔ Идея

**Поле:** сбор внешней информации, без автоматического утверждения её значимости.

**Материальное:** Автор отбирает карточки; ИИ выполняет базовую обработку подборки: наблюдение, сопоставление, резонансный анализ, выявление напряжений и потенциалов, подготовку карты поля. Он не инициирует идею и не утверждает направление. При наличии уже заданной идеи проверяет соответствие материалов ей. Не принуждать несвязанные материалы к единой концепции. Фокус текущей карточки не отменяет контекста холста. Итог — основание и вопросы для сферы Идея, а не самостоятельно утверждённая идея.

**Идея:** Автор инициирует идею — выбирает, какой потенциал из подготовленного поля сделать своим направлением. ИИ в этой сфере помогает проявить авторское намерение, сформулировать версию идеи и её инварианты, обсуждает альтернативы; только Автор утверждает результат. Обратная связь `Материальное ↔ Идея` — предметный цикл уточнения, но не самовольное изменение данных.

Пять внутренних уровней по последнему авторскому решению: **Идея → Концепт → Прототип → Образец → Продукт**. На каждом уровне допустимы итерации; возврат на ранний уровень сохраняет историю. Полная автоматика переходов ещё не реализована.

## 7A. Резонансное поле, проявление потенциала и инициация

**Происхождение:** уточнение Автора от 2026-11-15; перекликается с ранее обсуждавшимися принципами UNO/SaS: «Внимание → Инсайт (маркер) → Связь → Поле → Форма» и с калибровкой на границе резонансов (субъективного отклика), интерпретаций и фрагментов наблюдаемой реальности. Этот слой — **интерпретационная модель творчества**, а не утверждение об измеримой физической вибрации предметов.

**Положение в архитектуре:** не новая функциональная сфера, не дополнительный вертикальный уровень. Это *механизм работы внутри связки «Материальное ↔ Идея»*, который может использоваться и на последующих итерациях.

### Определения

- **Отдельное звучание материала:** субъективно воспринимаемый характер объекта — напряжённость/спокойствие, плотность/воздушность, импульс/статичность, ритм, контраст, образы, эмоциональный отклик и т.д. «Вибрация» и «аккорд» здесь — язык Автора для опыта восприятия, не частотное измерение.
- **Резонанс:** предполагаемое взаимное усиление, противопоставление или согласование характеров материалов. Не требует внешнего сходства, единой типологии, совпадения цвета либо функции.
- **Резонансное поле / аккорд:** целостное образно-смысловое впечатление от сочетания материалов, включая отношения, паузы, контрапункт и напряжения. Может существовать до словесного определения идеи и до предметной формы.
- **Потенциал:** ещё не выбранная возможность развития этого поля в образ, намерение, идею, пространство или объект. Не выдавать предложенный вектор за неизбежный.
- **Инициация (в сфере «Идея»):** момент, когда Автор распознаёт значимый для него образ/напряжение/вектор среди подготовленных потенциалов и сознательно начинает развивать одну из возможностей. ИИ может предложить или уточнить такой вектор, **но не объявляет авторскую инициацию произошедшей**.
- **Проявление идеи:** осмысленная артикуляция выбранного потенциала. Результат может сначала быть *образным* (слова-маркеры, схема, композиция, референс) и лишь позднее стать текстовым определением, концептом или формой.

### Рабочая последовательность

`Материальное: внимание → наблюдение и субъективный отклик → отношения и аккорд → карта резонансного поля → возможные потенциалы` → `Идея: авторская инициация → уточнение намерения с ИИ → черновик идеи → утверждение Автором`.

Последовательность не предписывает обязательную прямую линию: Автор может начать с уже существующего намерения, затем проверять его на резонанс с подборкой; несколько «аккордов» могут сосуществовать. Возврат к материалам и смена композиции допустимы.

### Задача ИИ

1. Описывать **доступные наблюдаемые качества** объектов отдельно от образного отклика на них.
2. Предлагать **гипотезу общего звучания/поля**, допуская контраст и диссонанс как содержательные элементы композиции.
3. Не сводить анализ к поиску сходств: цвет, форма, категория и функция — лишь возможные маркеры, не доказательство ядра.
4. Предлагать не более двух **потенциальных направлений проявления**, не обязательно предметных; может быть настроение, состояние, пространственный образ или смысл.
5. Уточнять у Автора, что действительно созвучно его восприятию, что кажется чуждым, что инициирует движение. **Ответ Автора важнее интерпретации ИИ**.
6. Если общего аккорда не проявляется, оставить отдельные голоса/композиции вместо принудительного объединения.
7. При возможной фиксации передавать в «Идею» **карту поля**: выбранные материалы и связи, словесные/визуальные маркеры, напряжения, потенциалы, авторские уточнения, статус `draft`. Не подменять её автоматически одобренной идеей.

### Дисциплина достоверности

- «Звучит», «вибрирует», «резонирует» — метафоры/описания субъективного восприятия, пока не заданы физические измерения; ИИ не обладает специальным чувством физического поля.
- Всякая характеристика типа «объект несёт тревогу» — *возможная интерпретация*; наблюдение должно опираться на действительно доступные детали материала.
- Разделять **сигнал/наблюдение → интерпретация → гипотеза → калибровка с Автором**. Не выдавать личное ощущение Автора за универсальную реакцию всех людей.
- ИИ не вправе присваивать Автору намерение и не должен насильно переводить доречевой/образный опыт в «готовую идею».
- Сфера «Материальное» выполняет первичную обработку и выявление потенциалов, **но не инициирует идею**. В сфере «Идея» **Автор инициирует** выбранный потенциал; ИИ помогает его раскрывать, выражать и развивать. Подтверждение/утверждение остаётся за Автором.

## 7B. Уровни, глубина исследования и широкий охват сфер (решение Автора, 2026-11-15)

**Два разных значения «Идея»:** сфера **Идея** — место авторской инициации; уровень **01 «Идея»** — первая степень зрелости всего проекта. Первый полный круг восьми функциональных сфер и синтез Желтка запускается **уже на уровне 01**, а не после перехода к «Концепту». Инициация сама по себе ещё не запускает цикл до явного авторского действия и соблюдения условий движка.

### Пять уровней и изменение рабочей глубины

| Уровень | Глубина / задача сфер | Что НЕ требуется по умолчанию |
| --- | --- | --- |
| **01 Идея** | Первичное восприятие, потенциал, принципиальные вопросы, заметные напряжения, возможности | Полное ТЗ, окончательная форма, точные сметы, физические испытания |
| **02 Концепт** | Проекция замысла: образ и визуализация, пространственный принцип, альтернативы, предварительная логика | Подтверждение изготовляемости художественной картинкой |
| **03 Прототип** | Эксперименты и проверки ключевых гипотез; фиксация наблюдаемого и непроверенного | Объявление мысленного эксперимента реальным испытанием |
| **04 Образец** | Предметная детализация, соответствие принятой концепции, качество и пригодность экземпляра | Подмена реального образца неподтверждённым изображением |
| **05 Продукт** | Готовность воплощённой продуктовой формы к своему назначению: эксплуатация, передача, показ, производство или лицензирование — по фактической модели | Обязательная серийность, продажи или масштабирование |

**Уровень задаёт типичную глубину, но не жёсткий объём работы.** Если сфера «Право» уже на уровне 01 обнаруживает потенциально критичное препятствие, требуется углублённое исследование конкретного риска. Если на уровне 05 вывод ранее проверен и актуален, не нужно исследовать его заново ради видимости активности.

### Охват сферы — назад, здесь и вперёд

**Охват** — отдельная ось, не тождественная глубине. Каждая из восьми сфер видит:
- **Назад:** происхождение замысла, утверждённую ДНК, предшествующие версии/решения/противоречия, *насколько они доступны и разрешены*.
- **Здесь:** задачу, соответствующую текущему уровню зрелости, текущую итерацию и входы своей ветви.
- **Вперёд:** вероятные последствия для следующих уровней, будущие требования, ограничения и траектории как *гипотезы для проверки*, а не знания о будущем.

**Сфера может воспринимать значительно шире, чем должна прорабатывать.** Предварительный сигнал о будущей технологии на первом уровне не требует сейчас разрабатывать технологическую карту; однако его следует удержать в выходном пакете как открытый вопрос с происхождением и приоритетом.

**Важные ограничения:** широкий охват не означает доступ ко всем данным проекта. В текущем движке сфера видит только переданный срез ДНК, своей ветви и свою историю; результаты другой ветви текущей итерации сопоставляются в Желтке. Не выдумывать прошлые факты и будущие результаты, не превращать прогноз в подтверждённый факт.

### Синтез и решение

На каждом уровне схема одна:
`Инициация Автором / опорная версия → итерация восьми сфер (две ветви) → единый вклад каждой сферы: текущий результат + выявленные прошлые/будущие сигналы → Желток → решение Автора (итерация / принятие уровня / возврат)`.

Желток оценивает **достаточность проработки применительно к текущему уровню**, а не абстрактную максимальную детализацию. При этом существующий `EggYolkSynthesis` пока структурно собирает результаты, пробелы и вопросы; оценка достаточности и визуальный мониторинг — **целевое требование**, не автоматически реализованная экспертная оценка.

Каждое принятие уровня закрепляет версию-опору. Возврат с новыми сведениями не стирает историю — движение по спирали; решение о возврате/изменении ДНК принадлежит Автору.

### Проекция в интерфейс Яйца

- Пять точек вертикальной оси должны показывать **текущий уровень**, **принятые уровни** и **ещё не пройденные**, а также **номер итерации**.
- Подсветка функциональных сфер — реальный статус текущего круга: ожидает, работает, передала результат, требует внимания; анимация не должна выдавать имитацию за действие ИИ.
- Желток отражает завершение обоих потоков, наличие синтеза и ожидание авторского решения.
- Состояние подсветки следует брать **из серверного состояния проекта и `flowCycles`**, а не из отдельного `localStorage` «демо-уровня». До этой интеграции текущая подсветка в `UnoEggScene` — локальный прототип, не достоверное представление хода серверного цикла.
- Мастерская «Идея» должна явно передавать *согласованную Автором версию намерения* в запуск первого полного цикла. **Текущее локальное сохранение черновика и запрос к idea-dialogue ещё не означают запуск движка или принятие ДНК.**

### Интеграционный статус

Реализовано в `src/lib/eggSphereProtocol.ts`: `EGG_LEVEL_DEPTH` и `buildEggSpherePerceptionInstruction(level)`; в `src/lib/eggSphereIntelligence.ts` этот контракт передаётся в реальные задания ИИ всех восьми функциональных сфер. **Не реализовано:** серверная связка черновика «Идея» с первым кругом, серверно-истинная подсветка всей оси и фаз, экспертная оценка достаточности в Желтке, управляемые возвраты между всеми уровнями. Не считать эти функции опубликованными до успешной сборки и проверки.

## 7C. Желток как накопительный синтез слоёв и ранняя диагностика итераций (авторское уточнение, 2026-11-15)

**Смысл:** Желток — не финальная сводка после позднего прототипирования, а центральное место, где *с самого первого круга уровня «Идея»* собираются разные слои восприятия восьми сфер. Их совместное рассмотрение обнаруживает несоответствия задолго до материальной проверки. Это механизм формирования целостности, а не автоматического изготовления ответа.

**Работа каждого круга:**
1. Сфера «Идея» принимает инициацию Автора, помогает проявить замысел и возможный аккорд/ДНК (сначала кандидат, а не навсегда утверждённый факт). «Материальное» подготавливает образно-смысловое поле и контекст.
2. Восемь функциональных сфер исследуют текущую версию **на глубине данного уровня** с охватом прошлого, настоящего и возможного будущего. Даже поверхностное рассмотрение на уровне 01 может обнаружить критический вопрос к последующим стадиям.
3. Каждая сфера отдаёт **один** вклад: результат текущей задачи и значимые сигналы о несоответствиях или будущих последствиях. Последовательный поток развивает ветвь, радиальное направление передаёт тот же результат Желтку без повторной AI-обработки.
4. Желток сопоставляет ДНК/намерение, результаты обоих потоков, источники, несогласия и пробелы; **сравнивает текущую итерацию с предыдущими**. Это позволяет различать: обнаружено → исследовано → подтверждено/опровергнуто → остаётся открытым; а также замечать новые несоответствия.
5. Автор по целостному результату принимает решение: уточнить и повторить круг на том же уровне, перейти дальше при достаточной согласованности или адресно вернуться назад. Коррекция ДНК возможна только по явному решению Автора, с сохранением предыдущей версии и причин.

**Цель итерации — уменьшить *значимую* неопределённость**, а не накапливать всё больше текста, карточек и гипотез. Не требуется ликвидировать вообще все неизвестные до перехода: важно различать критические для текущего уровня риски и вопросы, которые можно обоснованно перенести на следующий.

**Спецификация будущего сравнения:** по каждому несоответствию сохранять идентификатор, происхождение/сферы и версии, уровень и итерацию обнаружения, формулировку и статус достоверности, предполагаемое влияние, адресуемый уровень/сферу, предпринятое действие, результаты повторной проверки и решение Автора. Отсутствие данных не приравнивать к разрешению проблемы.

**Различие двух инвариантов:** ДНК удерживает распознанный Автором смысловой аккорд текущей версии, а Желток удерживает и перерабатывает развивающиеся сведения об объекте. ДНК может быть скорректирована по авторскому решению — не автоматически от каждой новой гипотезы.

**Актуальное предложение по названиям пяти уровней:** `Идея → Концепт → Проект → Прототип → Объект`. Это более поздняя архитектурная гипотеза, чем действующая шкала `Идея → Концепт → Прототип → Образец → Продукт`; её **ещё не переносили в `EGG_LEVEL_DEPTH`, UI или flow-engine**. Следует синхронизировать названия и критерии одним отдельным проверяемым изменением, а не незаметно менять старую историю.

**Состояние реализации:** текущий `EggYolkSynthesis` в `src/lib/eggFlowCycle.ts` структурно собирает ветви, вопросы и пробелы, но не ведёт полноценный реестр несоответствий между итерациями и не вычисляет экспертную достаточность. Изложенное — **согласованное направление для реализации**, не заявка на уже работающую функцию.

## 8. Предметные роли восьми сфер

| Сфера | Роль ИИ | Что создаёт | Граница |
| --- | --- | --- | --- |
| Маркетинг | Исследователь контекста, пользователей, спроса и альтернатив | Сигналы и проверяемые гипотезы ценности | Не объявляет спрос доказанным |
| Дизайн | Исследователь формы, функции и пространственного опыта | Одна развиваемая версия формы/эскиза с вопросами | Не выдаёт эскиз за чертёж |
| Тестдрайв | Критический проверяющий сценарии реального использования | Карта проблем, проверок и обратной связи | Не изображает виртуальное исследование физическим испытанием |
| Коммерция | Аналитик экономики текущей версии | Диапазоны/сценарии и неопределённость, если есть исходные данные | Не выдумывает цены, не принимает UNOcalc за рыночную смету |
| Право | Исследователь прав, ограничений и лицензий | Реестр правовых вопросов, источников и рисков | Не выдаёт юридическую очистку или заключение без проверки |
| Производство | Исследователь технологической осуществимости | Возможные технологии, узлы, ограничения, проверки | Не сертифицирует конструкцию |
| Комплектация | Исследователь материалов, компонентов и поставок | Возможные спецификации и альтернативы | Не выдумывает наличие, цену или срок |
| Ритейл | Архитектор представления и сценария контакта с аудиторией | Один сценарий показа текущей версии | Не объявляет продажи или готовность продукта |

Это **первичные роли**, уже согласованные с предметными линзами `EGG_SPHERE_LENSES`. Для каждой сферы отдельный полноценный manifest и его способности уточняются на практических кейсах.

## 9. Контроль и безопасность

- Не изменять ДНК, утверждённые версии, уровень, авторство или маршрут по текстовой инициативе AI.
- Не утверждать гипотезы как факты; у фактов сохранять источник, дату и границу наблюдения.
- Не выдавать отсутствующие инструменты и доступы за включённые способности.
- Заказ, платёж, отправка внешних сообщений, публикация, выдача лицензии, изменение разрешений требуют явного разрешения и отдельной операции.
- Не создавать скрытых повторных запросов AI для одного и того же вклада только потому, что он участвует в двух потоках.
- Сохранять несогласия, альтернативы, историю версий и причины возврата.
- При неготовности результата сообщать честный статус, а не имитировать завершение сферы.
