# «Яйцо» v0.7 — независимость от Lovable

Архитектурное решение: **Lovable — исторический инструмент разработки существующего сайта, НЕ системная зависимость движка «Яйцо»**.

## Проверенные факты (03.11.2026)

- В репозитории существуют автоматически генерируемые Lovable файлы \`src/integrations/supabase/client.ts\` и \`previewAuthStorage.ts\`. Они обслуживают существующий сайт.
- В \`supabase/config.toml\` записан ID Supabase проекта существующего сайта; это не основание подключать к нему «Яйцо».
- Через Lovable database status подтверждено: у существующего проекта включена база Supabase. В таблицах \`public\` существующей базы \`egg_engine_*\` до этого не было.
- Vercel API для «Яйца» ранее имел fallback \`EGG_SUPABASE_URL || VITE_SUPABASE_URL\`, потенциально смешивавший независимый движок и базу сайта.
- Подключённый пользовательский Google Drive работал независимо от Lovable; он не требует облачной базы Lovable.

## Принятая архитектура

\`\`\`text
ЧЕЛОВЕК → привычный ИИ → EGG API / MCP → ДВИЖОК «ЯЙЦО»
                          |                |
                          |                └── Отдельная база Egg (первый пилот: Supabase/Postgres)
                          └── Google Drive пользователя (через ИИ, независимо)
\`\`\`

**Платформа Lovable не находится внутри этого контура.** Если Lovable перестанет существовать или пользователь захочет другой сайт, движок и данные должны оставаться работоспособными.

Технический контракт движка — JSON, версия проекта, авторские разрешения и адаптер MCP. Supabase — **выбранный способ реализовать первую базу**, а не обязательная часть продуктового метода. Перенос на обычный PostgreSQL будет отдельной задачей; пока он не реализован.

## Изменения в тестовой ветке

1. Добавлен серверный модуль \`api/_eggStorageConfig.ts\` с **обязательными отдельными** переменными:
   - \`EGG_SUPABASE_URL\`
   - \`EGG_SUPABASE_PUBLISHABLE_KEY\`
   - \`EGG_SUPABASE_SERVICE_ROLE_KEY\`
2. Удалены fallback на \`VITE_SUPABASE_URL\`, \`VITE_SUPABASE_PUBLISHABLE_KEY\` и глобальный \`SUPABASE_SERVICE_ROLE_KEY\`. Если три Egg значения не указаны, API **закрыт** с 503.
3. Добавлена предупредительная проверка: явный URL Egg не может указывать на ту же Supabase-hostname, что \`VITE_SUPABASE_URL\`. Дополнительно при реальном подключении нужно независимо проверить фактическую базу, особенно если проект использует alias/custom-domain.
4. Миграция движка перенесена из \`supabase/migrations/\` сайта в **\`egg-server/migrations/\`**. Автоматическая миграция сайта больше не должна подхватить эти таблицы.
5. Добавлены regression tests настройки изоляции.

## Чего ещё нет

- Отдельный Supabase project для Egg не создан и SQL туда не применён.
- Не подключены авторские пользовательские сессии к отдельному сервису Egg.
- OAuth/SSO, при котором автор может продолжать пользоваться одной учётной записью, потребует отдельного проектирования. Отделение БД не должно принуждать пользователя к двум чатам или повторной передаче личного контекста.
- Нет Postgres-адаптера и теста миграции данных между провайдерами.
- Нет включённого сервера для реальной регистрации файлов: \`/api/mcp\` и \`/api/egg\` пока намеренно закрыты до отдельной настройки.

## Запреты на следующие шаги

- **Не выполнять миграцию Egg против рабочей базы Lovable Cloud.**
- Не помещать секреты \`EGG_*\` в исходники, \`VITE_*\`, браузерные настройки или пользовательские документы.
- Не подменять независимую базу переименованием переменных: проверить настоящий ID Supabase проекта и среду развёртывания.
- Не менять \`src/integrations/supabase/client.ts\` существующего сайта без отдельной миграционной задачи: это может нарушить текущие сервисы и авторизацию.

## Следующая операционная задача

Поднять **собственную тестовую базу Egg**, применить отдельную миграцию, проверить создание проекта, запись и чтение через API/MCP, отзыв agent key и подтверждение Автором. После этого подключить авторскую страницу к серверу. До момента проверки работа остаётся в изолированной тестовой ветке GitHub/Vercel.
